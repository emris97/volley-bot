# Доступ агента к production VDS по SSH

Этот runbook предназначен для агента, которому пользователь явно поручил
диагностику или обслуживание production-сервера Volley Bot. Наличие инструкции
не является разрешением менять сервер: без отдельного запроса разрешены только
проверки, не изменяющие состояние.

## Сервер и приложение

- SSH-алиас: `volley-bot-prod`
- Хост: `npoletaev97.fvds.ru`
- SSH-порт: `22`
- Текущий администратор: `root`
- Репозиторий на сервере: `/opt/volley-bot`
- Production-окружение: `/etc/volley-bot/production.env`
- Основной Compose-файл: `/opt/volley-bot/compose.yaml`
- Production override: `/opt/volley-bot/compose.prod.yaml`
- Health-check: `https://npoletaev97.fvds.ru/health/ready`

Прямой доступ под `root` обладает полными правами. Используй его только в
рамках явно поставленной пользователем задачи. Для автоматического CD должен
использоваться отдельный ограниченный пользователь `volley-deploy`, описанный в
плане `docs/superpowers/plans/2026-09-05-github-actions-vds-cd.md`.

## Локальная настройка SSH

Приватный ключ хранится только на машине оператора. Не добавляй ключ, пароль,
его содержимое или абсолютный путь к нему в Git, задачи, логи либо сообщения.
Агент, работающий на другой машине или в облаке, автоматически доступа к этому
ключу не получает.

На машине, с которой выполняется подключение, добавь запись в SSH config:

```sshconfig
Host volley-bot-prod
    HostName npoletaev97.fvds.ru
    User root
    Port 22
    IdentityFile ~/.ssh/volley_bot_prod
    IdentitiesOnly yes
```

Файл конфигурации расположен в `~/.ssh/config`; в Windows OpenSSH это обычно
`%USERPROFILE%\.ssh\config`. Значение `IdentityFile` настраивается локально и
может отличаться от примера. Сам файл ключа не должен находиться внутри
репозитория.

Перед первым подключением получи отпечаток host key через консоль хостинг-
провайдера или уже доверенный канал и сравни его с отпечатком, показанным SSH.
Не отключай `StrictHostKeyChecking` и не принимай изменившийся ключ без проверки.

Проверить, как раскрывается локальная конфигурация, без подключения:

```sh
ssh -G volley-bot-prod
```

Проверить неинтерактивную аутентификацию:

```sh
ssh -o BatchMode=yes volley-bot-prod 'id -un && hostname'
```

Ожидается пользователь `root` и имя production-хоста. Ошибка `Permission denied`
означает, что подходящий приватный ключ недоступен; не проси отправить его в чат.

## Безопасный порядок работы агента

1. Кратко сообщи пользователю, что собираешься проверить.
2. Начни с команд только для чтения и зафиксируй текущее состояние.
3. Не показывай содержимое environment-файлов, ключей, токенов и заголовков
   авторизации.
4. Перед установкой пакетов, правкой файлов, миграцией, перезапуском, деплоем,
   изменением firewall или SSH запроси явное разрешение, если действие не было
   прямо поручено.
5. Перед изменением файла создай ограниченную резервную копию конкретного файла;
   не копируй секреты за пределы сервера.
6. Не выполняй `git reset --hard`, `git clean`, рекурсивное удаление, удаление
   Docker volumes и команды `docker compose down -v`.
7. После разрешённого изменения проверь контейнеры и readiness, затем сообщи
   пользователю точный результат без секретов.

## Первичная диагностика

Сначала убедись, что подключён к ожидаемому серверу и checkout существует:

```sh
ssh volley-bot-prod 'hostname; uptime; test -d /opt/volley-bot && git -C /opt/volley-bot status --short --untracked-files=no && git -C /opt/volley-bot rev-parse --short HEAD'
```

Показать состояние production-контейнеров:

```sh
ssh volley-bot-prod 'docker compose --env-file /etc/volley-bot/production.env -f /opt/volley-bot/compose.yaml -f /opt/volley-bot/compose.prod.yaml ps'
```

Проверить публичную готовность API:

```sh
ssh volley-bot-prod 'curl --fail --silent --show-error https://npoletaev97.fvds.ru/health/ready'
```

Посмотреть ограниченный фрагмент свежих логов API и worker:

```sh
ssh volley-bot-prod 'docker compose --env-file /etc/volley-bot/production.env -f /opt/volley-bot/compose.yaml -f /opt/volley-bot/compose.prod.yaml logs --since=30m --tail=200 api worker'
```

Логи могут содержать Telegram ID и другие операционные данные. Анализируй их в
текущей защищённой сессии и не вставляй полный вывод в публичные места. В отчёте
приводи только необходимые обезличенные строки.

## Изменения и восстановление

Не редактируй production checkout вручную и не запускай `git pull` без понимания
принятого процесса деплоя. После реализации CD штатный деплой выполняется только
GitHub Actions, а ручной rollback — серверным wrapper из operations-плана.

Перезапуск контейнера, миграция базы или rollback могут прервать работу либо
необратимо изменить данные. Выполняй их только по явному запросу пользователя и
согласно актуальной production-инструкции. После любого такого действия выполни
`docker compose ... ps` и readiness-проверку из предыдущего раздела.

## Что сообщить при проблеме

В безопасный отчёт входят:

- доступен ли SSH и совпал ли host key;
- имя проблемного сервиса и его состояние;
- короткий SHA текущего checkout;
- HTTP-статус readiness;
- время и обезличенный текст релевантной ошибки;
- предложенное следующее действие и его риск.

Никогда не включай в отчёт приватный ключ, `BOT_TOKEN`, webhook secret,
`DATABASE_URL`, `REDIS_URL`, пароли, полный environment-файл или необработанные
пользовательские данные.
